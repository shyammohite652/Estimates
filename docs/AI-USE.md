# AI use

An honest record of how AI was used to build this submission, what was rejected or rewritten, and
which parts deserve the closest review.

## Tools and what they did

| Tool | Used for |
|---|---|
| **Claude (Anthropic), agentic coding session** | Read the brief, wrote `DESIGN.md` and the ADRs, then generated the backend, frontend, tests, docs and git history in one session. It ran builds, tests and HTTP end-to-end checks in a cloud workspace. |
| Developer's brief to the AI | Set the stack (ASP.NET Core / EF Core / SQL Server / Angular), the layer structure, the rules to prioritise and the deliverables. The design decisions in DESIGN §2 were taken by the AI, reasoning from the brief, and are written down so they can be challenged. |

**Constraints the AI worked under.** These shaped some of the code:
- The workspace had no access to nuget.org, Docker registries or SQL Server. NuGet packages were copied
  from the developer's local NuGet cache. That is why FluentValidation and NetArchTest are not used: they
  weren't available, and the reasons they aren't *needed* are recorded in ADR-003.
- The EF Core design-time package (`dotnet ef`) was not available, so the migration was generated by a
  small throwaway program. It used EF Core's runtime model differ and fed the resulting operations
  through a code emitter. The output was verified two ways: `HasPendingModelChanges()` is `false`
  (now a permanent test), and all 21 DDL statements in the migration's script exactly match the DDL
  EF generates from the model (`docs/database/InitialCreate.sql`).
- The full API was exercised over HTTP against the in-memory provider (32 scripted checks across R2–R18,
  kept out of the repository), and the UI was checked with Playwright screenshots. **It has not been run against a real
  SQL Server** by the AI.

## Output that was rejected or rewritten

### 1. Value converters on money → plain decimals written only through value objects

The first version mapped `Money`/`Quantity`/`MarkupPercentage` straight onto the entity with EF value
converters. It looked like "types make invalid states unrepresentable". In practice it forced a
provider-specific trick into every aggregate, and the totals query crashed on a non-relational provider.

**Before** (`EstimateQueries`, after first replacing raw SQL):
```csharp
// The (decimal)(object) cast is how EF Core is told to aggregate the stored provider value of a
// value-converted property; it translates to SUM(CAST([LineTotal] AS decimal(18,2))).
.Select(g => new LineTotalsRow(
    g.Count(),
    g.Sum(l => (decimal)(object)l.NetAmount),
    ...
```
and in the entity:
```csharp
public Money LineTotal { get; private set; }
public Quantity Quantity { get; private set; }
```

**After:**
```csharp
public decimal LineTotal { get; private set; }   // written only in Reprice(Quantity, MarkupPercentage)
public decimal Quantity { get; private set; }

internal void Reprice(Quantity quantity, MarkupPercentage markup)
{
    Quantity = quantity.Value;
    ...
    var amounts = LinePricing.Calculate(quantity, Money.FromExact(UnitRate), ...);
    LineTotal = amounts.Total.Amount;
```
```csharp
.Select(g => new LineTotalsRow(g.Count(), g.Sum(l => l.NetAmount), ...))
```
**Why:** the invariant still holds. Nothing can write an unvalidated or unrounded amount, because the
only writers take value objects, and an architecture test forbids public setters. Meanwhile queries,
mappings and migrations got simpler. The cast trick was clever, but it had to be explained, and it was
fragile.

### 2. Raw SQL for totals → LINQ

The first version computed header and project totals with `Database.SqlQuery<T>($"SELECT COUNT(*) ...
FROM EstimateLines ...")`. It was rewritten to LINQ `GroupBy/Sum`, which produces the same single
aggregate query without table and column names hard-coded in strings that refactors and migrations
can't see.

### 3. A meaningless test the AI wrote, caught and rewritten

While writing the approval-concurrency tests, the AI produced this. It compiles, passes, and proves nothing:
```csharp
await Assert.ThrowsAsync<ConflictException>(async () =>
{
    await service.ApproveAsync(estimate.Id, Ct);
    // unreachable when the status re-read is Approved; force the non-approved branch below
}).ContinueWith(_ => Task.CompletedTask).Unwrap().ConfigureAwait(false) is var _ ? Task.CompletedTask : Task.CompletedTask;
```
**After:** the fake gained an explicit `StatusOverride`, so the test states its scenario: the save
conflicts, *and* the committed row shows someone else rejected the estimate. So the approval must
surface a 409 rather than pretend to succeed:
```csharp
_world.SaveFailures.Enqueue(new ConflictException("rowversion"));
_world.StatusOverride = EstimateStatus.Rejected;
await Assert.ThrowsAsync<ConflictException>(() =>
    _world.ServiceFor(Reviewer, UserRole.Reviewer).ApproveAsync(estimate.Id, Ct));
```

### 4. Over-strict assertion

The R17 test first asserted that the serialized estimate contained no "labour" substring anywhere. It failed on
the legitimate capability flag `canViewLabourCost`. It was narrowed to the actual data field
`"labourTotal"`. The point is that a failing test had to be read, not just "fixed".

### 5. Vulnerable transitive packages, caught on the first local build

The AI's builds ran offline, so NuGet's vulnerability audit never ran. On the first build on a real
machine, `TreatWarningsAsErrors` turned audit warnings into 8 errors: System.Security.Cryptography.Pkcs
9.0.4 (via SqlClient, GHSA-846f-f764-76mx and GHSA-2fmv-rv2c-59x7) and Microsoft.OpenApi 2.3.0 (via
Swashbuckle, GHSA-v5pm-xwqc-g5wc). The fix pins the patched versions (10.0.13 and 2.7.5) as direct
references, each with a comment saying when to remove it. Suppressing NU1902/NU1903 would also have
made the build pass, but it would have removed a useful gate.

### 6. Seeder transaction vs. the retrying execution strategy, caught on the first SQL Server run

The seeder called `BeginTransactionAsync` directly, but SQL Server is configured with `EnableRetryOnFailure`.
EF Core refuses user-started transactions under a retrying strategy, because a retry could replay half a
transaction. The in-memory runs couldn't catch this. The fix wraps the whole seed in
`Database.CreateExecutionStrategy().ExecuteAsync(...)` and clears the change tracker at the start of each
attempt. This is the reason integration tests against real SQL Server are the first item under "next steps".

## Parts that need the closest review

- **Migration files** (`Persistence/Migrations/*`). Generated by a tool, not written by hand; verified as
  described above. They can be regenerated with `dotnet ef migrations add InitialCreate` (after adding
  the EF design package); `MigrationTests` confirms the result.
- **`EstimateService.ApproveAsync` concurrency path.** On a rowversion conflict the status is re-read
  rather than the save retried; the filtered unique index remains the database-level guarantee.
- **`Estimate` has no `Lines` collection.** This is the central aggregate trade-off for R19. Alternatives
  considered: a loaded collection (does not scale) or a separate Line aggregate (loses the Draft-only guard).
- **Line edits bump the estimate's rowversion** (`Touch`). Consequence: concurrent line edits on the same
  estimate conflict with a 409.
- **`ApiExceptionHandler` status mapping.** 400 invalid input, 403 role/R16, 404 missing or not assigned,
  409 state or concurrency conflict, 422 business rule.
- **Material theme and SCSS.** Generated styling; low risk.
